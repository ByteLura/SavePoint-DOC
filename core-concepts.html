Core concepts

SaveData — one typed store

A SaveData is a typed key-value store. Accessors cover int, long, float, double, bool, string, Vector2, Vector3, Quaternion, Color, and string/int/float arrays; arbitrary [Serializable] objects go through SetObject<T> / GetObject<T>. Custom serializers register per type with SavePoint.RegisterSerializer<T>. Keys are case-sensitive strings; enumeration is sorted-ordinal.

Serialization is deterministic: the same SaveData always produces the same bytes (sorted keys, invariant-culture numbers). A save file is a fixture-grade artifact — diffable, hashable, testable.

Two envelopes

  • JSON envelope — the whole store as one deterministic JSON document. Human-readable and diffable.
  • Binary envelope — magic SPP1, a format-version byte, flags (encrypted; compression is never used in v1), payload length, a SHA-256 of the payload, then the payload.

Every read verifies the envelope checksum before anything is trusted.

Profiles and slots

A profile is a player identity (id + display name). Each profile owns 10 named slots. Profiles are unlimited and fully isolated: no API surface lets one profile read another's slots.

A profile registry file (profiles.spp, atomic and checksummed, unencrypted — metadata only, never game data) lists profiles and per-slot metadata: slot name, created UTC, modified UTC, playtime seconds, data version, and a game-supplied summary string such as "Level 3 — 42 coins".

Saving to a new slot beyond 10 in one profile is rejected with a plain-language result; overwriting an existing slot is explicit. Deleting a slot removes its file chain.

The storage seam

All file access goes through ISaveStorage (Read / Write / Exists / Delete / List). The shipped FileSaveStorage is rooted at a configurable directory (default Application.persistentDataPath/SavePointPro). Because storage is an interface, platforms with different file rules implement the seam instead of forking the system.
